# Specify Protocol

- Use the selected project template for `spec.md`, or `change-template.md` when the entry decision permits one bounded change.
- `change.md` records Goal, Non-Goals, Scope, Acceptance Criteria, Verification, Result, and Handoff.
- `spec.md` records product context, observable boundaries, inherited constraints, stable IDs, and traceability where relevant; functional batches and vertical slices belong in Plan.
- Use four discussion stages in order. At each stage start, name the stage, its decision goal, its boundary, and its exit condition. Before moving on, summarize settled decisions, unresolved questions, and deferred topics; state whether the stage is ready to close, then wait for the user's explicit confirmation to end it. A summary or recommendation is not confirmation. Reopen an earlier stage when the user requests it or a later finding changes its decisions. Reuse established facts without repeating questions. Surface safety, quality, or inherited constraints as soon as they could change the current path or scope; do not defer consequential risks merely because a later stage covers them.
  1. Overall picture and main path: establish the problem, actors, desired result, and one typical end-to-end user path or event. Defer scope details, exceptions, and implementation unless they change this path. Close only when the user can explain the path and accepts the summary.
  2. Scope and business meaning: decide in-scope behavior, non-goals, and only the business concepts, state rules, and data semantics that affect this Feature. Name consequential invalid states or business invariants when relevant. Defer technical structures and exceptions that do not change scope or meaning. Close when the user accepts a concise scope and concept summary.
  3. Observable behavior and key exceptions: decide user-visible feedback, consequential failure or empty states, changed public API semantics, and quality scenarios that could change the design when relevant. State each quality scenario's conditions and verifiable outcome rather than a vague target. Discuss only exceptions that change product behavior or acceptance; leave internal design to Plan. Close when an implementer need not guess a caller-visible result or design-driving quality requirement.
  4. Acceptance and review: derive verifiable acceptance from the agreed path, scope, and key exceptions; present the document revision, Review Packet, gaps, and readiness recommendation. Close the discussion only on the user's explicit confirmation. For `spec.md`, separately request direct approval of the specific Spec revision; stage closure is not document approval.
- For one bounded change, combine straightforward stages into a brief discussion when useful. Name the combined stages and their boundaries, cover applicable decisions and risks, and wait for the user's explicit confirmation before closing the discussion.
- Discuss changed business boundaries, data semantics, and externally observable API contracts in Spec when relevant; resolve internal modules, data structures, and technical choices in Plan.
- Review the Review Packet, not every generated field.
- If a Feature already has an active contract of the other kind, stop and report the conflict. Archive or explicitly migrate the old contract with user approval; never leave both `spec.md` and `change.md` active.
