# ADR 审计检查清单

## 检查项 1：过时未标记

**目的**：识别代码现状已偏离、但 ADR 仍标记为 Accepted 的情况。

**方法**：

1. 提取每个 Accepted ADR 的决策摘要（从"决策"段落）
2. 对照代码库实际实现（通过 Grep、Read 或询问用户）
3. 若发现实质性偏离且无新 ADR 解释 → 标记异常

**偏离识别示例**：

- ADR 决策："使用 MyBatis 作为 ORM"
- 实际代码：大量出现 `@Entity`、`JpaRepository`
- 结论：已偏离，ADR 应被 Superseded

**输出字段**：

| 字段 | 说明 |
|------|------|
| ADR 编号 | 异常 ADR 的编号 |
| 决策摘要 | 一句话概括原决策 |
| 偏离证据 | 代码中的具体证据（文件路径、符号名） |
| 建议状态 | 通常为 `Superseded` |

## 检查项 2：冲突或重叠

**目的**：识别决策对象重叠但结论矛盾的 ADR 对。

**方法**：

1. 按主题（缓存、存储、消息队列、认证等）对所有 Accepted ADR 分组
2. 同主题内两两对比决策结论
3. 若存在矛盾 → 标记冲突对

**冲突识别示例**：

- ADR-003："使用 Redis 作为缓存"
- ADR-008："使用 Caffeine 作为本地缓存，不引入 Redis"
- 结论：冲突，需新建 ADR 仲裁

**输出字段**：

| 字段 | 说明 |
|------|------|
| ADR-A 编号 | 冲突方 1 |
| ADR-B 编号 | 冲突方 2 |
| 冲突点 | 决策对象 + 矛盾点描述 |
| 建议动作 | 新建仲裁 ADR / 标记一方为 Superseded |

## 检查项 3：撤销条件已触发

**目的**：识别撤销条件已被现实满足、但决策未被重新评估的 ADR。

**方法**：

1. 读取每个 Accepted ADR 的"撤销条件"段落
2. 提取每个可观测条件（QPS、延迟、团队规模等）
3. 通过 AskUserQuestion 询问用户当前项目指标，或从监控配置/代码注释中推断
4. 若条件被触发 → 标记异常

**触发识别示例**：

- ADR 撤销条件："单实例 QPS > 10k 时重新评估"
- 用户告知：当前峰值 QPS 12k
- 结论：条件已触发，需重新评估

**输出字段**：

| 字段 | 说明 |
|------|------|
| ADR 编号 | 被触发条件的 ADR |
| 被触发的条件 | 原文引用撤销条件 |
| 当前证据 | 指标值、数据来源 |
| 建议动作 | 重新评估 / 维持现状并更新条件 / 新建取代 ADR |

## 检查项 4：双向引用缺失

**目的**：识别 Superseded 状态但未正确建立版本关联的 ADR。

**方法**：

1. 扫描所有 Superseded 状态的 ADR
2. 检查 frontmatter 是否有 `superseded_by` 字段
3. 对于有 `superseded_by` 的 ADR，反向检查新 ADR 是否有 `supersedes` 指向它
4. 同理检查带 `supersedes` 字段的新 ADR，反向验证旧 ADR 状态

**缺失识别示例**：

- ADR-002 状态为 Superseded，但 frontmatter 无 `superseded_by`
- 或 ADR-005 的 `supersedes: ADR-002`，但 ADR-002 状态仍是 Accepted

**输出字段**：

| 字段 | 说明 |
|------|------|
| ADR 编号 | 缺失引用的 ADR |
| 缺失类型 | `superseded_by` 缺失 / `supersedes` 缺失 / 状态不一致 |
| 建议动作 | 补充 frontmatter 字段 / 同步状态 |

## 优先级判定

| 优先级 | 判定标准 |
|--------|---------|
| 🔴 High | 已造成实际偏差或冲突，影响团队决策 |
| 🟡 Medium | 撤销条件已触发，潜在风险但未爆发 |
| 🟢 Low | 元数据/引用缺失，不影响决策正确性 |

````markdown

- 总数：N
- 异常数：M
````
