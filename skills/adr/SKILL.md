# ADR（架构决策记录）

## 概述

每个架构决策都有两个生命周期：

- **技术生命周期**：架构方案能用多久，结束时意味着改换方案
- **知识生命周期**：做出决定的理由能存活多久，结束时意味着团队开始无意识地重复过去的错误

ADR 通过结构化文档捕获"为什么做这个选择"、"考虑了什么替代方案"、"什么条件下会重新考虑"，延长决策的知识生命周期。

本 Skill 提供两条工作流：**写 ADR**（工作流 A）与 **审计 ADR**（工作流 B）。

## 工作流入口：识别意图

进入 Skill 后，第一步是识别用户想走哪条工作流：

1. **原始消息已明确**（如"帮我写一份 ADR"、"记录这个架构决策"、"审计一下 ADR 目录"）：直接进入对应工作流
2. **意图不明确**（如只输入 `/adr`、"用一下 ADR"、"整理架构决策"）：使用 AskUserQuestion 询问

**询问方式**：

- 问题："本次想执行哪个工作流？"
- 选项：
  - **写 ADR（推荐）**：基于口述生成结构化 ADR 初稿，含 5 要素与生命周期
  - **审计 ADR**：扫描 `docs/adr/` 目录，输出过时/冲突/撤销条件已触发的异常清单

用户选择后，进入对应工作流。**不要在意图不明时擅自启动某一条工作流**——写和审计的输入需求完全不同，走错会浪费用户时间。

## 工作流 A：写 ADR

### 第一步：识别决策背景

判断用户输入的完整度：

- **信息齐全**：用户已提供决策背景、候选方案、最终决策 → 直接进入第三步
- **信息不全**：使用 AskUserQuestion 逐一询问三块信息
  1. 决策背景：当前技术问题、业务约束（团队规模、技术栈版本、时间压力）
  2. 候选方案：同期评估过的 2-3 个方案，各一句话描述
  3. 最终决策：选择了哪个方案 + 简要理由

### 第二步：加载模板规范

读取 [adr-template.md](references/adr-template.md) 获取：

- 5 要素详解表（背景 / 决策 / 后果 / 替代方案 / 撤销条件）
- 标准 ADR Markdown 模板（含 frontmatter）
- 字段填写要点

### 第三步：生成 ADR 初稿

基于用户输入填充模板。**重点引导用户补全两项易漏内容**：

- **后果**：要求至少 2 个正面 + 2 个负面/中性影响。若用户未提供，主动追问"采用后哪些问题被解决？引入了哪些新约束？"
- **撤销条件**：要求是**可观测**的条件/指标（如"QPS 超过 X"、"团队规模超过 Y"），而非主观判断（如"性能不行时"）

### 第四步：确定编号与路径

- 扫描目标目录（默认 `docs/adr/`）下已有的 `ADR-*.md`，取最大编号 + 1
- 若目录不存在，询问用户是否创建
- 文件命名：`ADR-{编号}-{kebab-case-短标题}.md`，例如 `ADR-007-use-redis-as-cache.md`

### 第五步：写入文件

使用 Write 工具创建文件。创建后告知用户：

- 文件路径
- 状态字段（默认 `Proposed`，待评审后改 `Accepted`）
- 下一步建议（如"提交 PR 评审"）

## 工作流 B：审计 ADR

### 第一步：定位 ADR 目录

- 默认扫描 `docs/adr/`
- 若不存在，使用 AskUserQuestion 询问实际路径
- 若目录存在但为空，告知用户无 ADR 可审计

### 第二步：加载审计清单

读取 [audit-checklist.md](references/audit-checklist.md) 获取 4 项检查：

1. 过时未标记
2. 冲突或重叠
3. 撤销条件已触发
4. 双向引用缺失

同时读取 [lifecycle-rules.md](references/lifecycle-rules.md) 了解状态语义与版本关联规范。

### 第三步：逐项核对

读取目录下所有 `ADR-*.md` 文件，对每个文件：

1. **过时未标记**：对比代码现状与 ADR 决策。若实际实现已偏离且无新 ADR 解释 → 标记异常
2. **冲突或重叠**：扫描所有 Accepted ADR，识别决策对象重叠但结论矛盾的记录 → 标记冲突对
3. **撤销条件已触发**：读取每个 ADR 的"撤销条件"段落，对比当前项目指标/场景（通过 AskUserQuestion 询问或从代码/配置推断）→ 标记被触发的条件
4. **双向引用缺失**：检查 Superseded 状态的 ADR 是否有 `superseded_by`，新 ADR 是否有 `supersedes` → 标记缺失

### 第四步：输出异常清单

按 [audit-checklist.md](references/audit-checklist.md) 中的"异常清单输出模板"生成 Markdown 报告，包含：

- 审计元信息（日期、范围、总数）
- 按优先级分组的异常清单（High / Medium / Low）
- 统计摘要与下一步建议

将报告输出到对话中，并询问用户是否需要保存为文件（如 `docs/adr/_audit-{YYYY-MM-DD}.md`）。

## 关键约束

1. **不可变原则**：ADR 一旦 Accepted，内容冻结。任何变更需新建 ADR，并在旧 ADR 末尾建立双向引用。
2. **状态字段枚举**：只能取 `Proposed` / `Accepted` / `Deprecated` / `Superseded`。
3. **编号单调递增**：不回收已废弃 ADR 的编号。
4. **状态变更需同步**：更新 frontmatter 状态、`最后修改` 日期与"变更历史"表格三者缺一不可。

详细生命周期规则见 [lifecycle-rules.md](references/lifecycle-rules.md)。
