# Agent-Friendly CLI

## 核心原则

CLI 是 AI agent 的原生接口：文本进出、可管道组合、退出码可预测、输出即审计日志。设计 CLI 时把「agent 可能会调用它」当前提——只有 GUI、没有文本接口的产品，agent 只能靠截图与坐标猜测，UI 一改就崩。

## 设计检查清单

设计或改造 CLI 时逐条对照。

### 1. 输出机器优先

- 默认输出结构化文本（JSON / YAML），人类可读的 pretty 输出作为可选格式
- 提供模式开关：`--json`（结构化）、`--quiet`（只给关键结果）、`--verbose`（诊断细节）
- 字段命名与类型跨调用稳定，让 agent 能可靠解析

### 2. 非交互默认

- 默认不弹 prompt、不阻塞等待人工确认
- 提供 `--yes` / `--force` / `--no-input` 显式跳过确认
- 交互式提示仅作为检测到 TTY 时的可选行为，不能是唯一路径，否则 CI/agent 会卡死

### 3. 渐进式 `--help`

让 agent 用最少调用获得刚好够用的信息，避免一次塞过多无关内容：

- **L0 命令摘要**：一行简述，供上下文注入，agent 据此决定是否深入
- **L1 完整用法**：无参 `tool --help` 返回子命令列表与基本用法
- **L2 参数级帮助**：`tool subcommand --help` 或缺参时返回具体参数含义与取值

### 4. 两层架构

把 CLI 从「能跑」变成「对 LLM 友好」的关键。两层职责必须分离。

**执行层（L1）——纯 Unix 语义**

- 命令路由、管道、退出码
- **必须无损、无元数据**：在执行层截断 `cat` 的输出，下游 `grep` 就只能搜前 200 行，结果不全
- 这一层保证管道可组合；任何截断或装饰都放到呈现层

**呈现层（L2）——为 LLM 的认知约束服务**

四个机制：

- **Binary Guard**：检测到二进制（图片、编译产物等）就拦截，不让无意义字节污染上下文。未拦会让 agent 拿到一堆乱码 token，瞎试很多轮才被强杀
- **Overflow Mode**：输出超阈值（如 200 行或 50KB）就截断，全文写临时文件，提示 agent 用 `grep` / `tail` / `head` 自己探查——把大数据探索变成模型本来就会的技能
- **元数据尾巴**：每条结果附 `[exit:0 | 1.2s]` 之类尾注，agent 看多了就内化「exit:1 要查错、耗时长要少调」
- **stderr 永不丢**：agent 既要知道失败了，也要知道为什么。绝不能因为 stdout 非空就丢 stderr——否则 agent 只知道「失败了」不知道「失败原因」，会盲试多种修正

### 5. 错误即导航

agent 不能搜索、不能问同事，接口要自带导航：

- 每个错误同时描述「哪里错了」和「如何解决」，让 agent 一步修正
- 反例：`Error: invalid input`
- 正例：`Error: --count must be a positive integer, got -3. Usage: tool --count N`

### 6. 稳定的输出契约

- 输出结构（字段、退出码、错误格式）跨版本稳定；变更走语义化版本，新版本先并存再逐步替换旧版本
- 退出码约定：成功 0，失败非 0；不同失败类型用不同码，方便 agent 分支处理
- 稳定结构让 agent 越用越准；不一致则每次都像第一次

## 反模式

- 在执行层（L1）截断输出 → 破坏管道正确性
- stdout 非空就丢 stderr → agent 不知失败原因
- 把二进制原样写进 stdout → token 污染
- 错误只说「失败」不说「怎么办」→ agent 盲试
- 一次 `--help` 塞数千字文档 → 淹没注意力
- 强制交互确认、无非交互逃逸口 → CI/agent 卡死

## 边界

CLI 不是万能。以下场景 CLI 主动输给 GUI/Web，别为「agent 友好」硬塞命令行：

- **非线性视觉信息**：看图、剪视频、调色、设计 UI——二维空间感知，字符网格承载不了
- **探索式数据交互**：滚百万行表格、缩放地图、大型代码库导航——需要低延迟空间移动
- **面向非技术终端用户的工具**：给设计师/产品/运营的工具应是 Web 应用（底层仍可用 CLI 子进程，再用抽象层藏起来）

> 准确命题：凡可能被 agent 用到的产品，都需要一个**机器可用的文本接口**（CLI / API / MCP 之一）。CLI 是其中对 agent 最自然的一种，但不是唯一解；三者按工具各司其职，而非系统一刀切。
