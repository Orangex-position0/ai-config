# 技术标题参考

用于技术视频的目的路由、表达风格选择和场景检查。下列示例是写作示例，不是已验证的爆款、平台公式或流量保证；只在输入材料支持时采用。

## 1. 按内容目的选择

先选一个主要目的，再选择表达风格；允许混合属性，不作一对一固定映射。

| 主要目的 | 观众需要判断什么 | 可优先考虑的表达 | 保留的信息 |
| --- | --- | --- | --- |
| 原理／概念讲解 | 什么现象、怎样理解 | 问题型、为什么型、心智模型型；确有认知差异再用冲突型 | 现象、概念或解释抓手 |
| 实操教程 | 能完成什么任务 | 问题型、成果表达、心智模型型 | 核心工具与具体成果，不堆技术栈 |
| 故障分析 | 是否为我的症状、怎么定位 | 症状表达、为什么型、问题型 | 辨识度高的错误或症状、案例范围、排查路径 |
| 源码／架构探索 | 跟到什么机制 | 源码探索型、问题型、心智模型型 | 项目名、一条真实机制或执行路径 |
| 对比／选型 | 我的约束适合哪个 | 决策型、问题型；确有结果再用认知冲突型 | 比较对象、任务或规模等决策条件 |
| 观点／经验分享 | 主张是什么、与我有何关系 | 为什么型、认知冲突型、反常识型 | 主张适用场景与材料中的理由 |

成果、症状等是表达方向，不必全部归入下面八种句式。先让标题对应实际问题或成果，再增加有依据的观看理由。

## 2. 八种表达风格

| 风格 | 结构抓手 | 使用条件 | 自拟示例 |
| --- | --- | --- | --- |
| 为什么型 | X 为什么会 Y？ | 内容确实解释原因，而非只展示绕过方法 | React 为什么要在开发环境重复运行 Effect？ |
| 认知冲突型 | 你以为 X，其实 Y；明明 X，为什么 Y？ | 材料支持认知差异，不将个别现象写成普遍真相 | 加了缓存，接口为什么反而更慢了？ |
| 问题型 | X 怎么工作／怎么做？ | 内容覆盖该问题的具体范围 | Coding Agent 如何调用工具？跟着一次请求看流程 |
| 误区型 | X 不只是 Y；关于 X 理解错了什么？ | 有明确误解及纠正依据；“很多人”也需要依据 | 播放完 Docker 教程，就等于会排错了吗？ |
| 心智模型型 | 用 N 个问题／一张图理解 X | 材料实际提供对应数量的框架或图，不先编数字 | 用一张流程图理解 Rc 的引用计数 |
| 源码探索型 | 跟着路径读 X；我读了 X，发现…… | 材料证明实际阅读路径；第一人称经历须有依据 | 跟着一次请求读 Gin：路由和中间件如何执行 |
| 决策型 | A vs B：在什么场景选哪个？ | 比较有具体约束，内容确实提供选择依据 | SQLite 和 PostgreSQL：个人项目该怎么选？ |
| 反常识型 | X 越……，为什么 Y 反而……？ | 有真实反直觉关系与解释，不能把相关写成因果 | 连接池越大，数据库为什么可能越慢？ |

不要为了覆盖风格更换实际承诺。故障案例可以在术语、症状和排查路径之间形成差异，而不必变成“颠覆认知”的观点视频。

## 3. 场景标签与承诺检查

标签只用于选择相关检查，不增加主分类或用户必填字段。通用真实性与输出规则以 `SKILL.md` 为准。

### 项目实战／入门／工具演示

- 项目实战突出一个真实成品或功能；本地演示限定在本地，不默认扩大为上线、跨设备或完整系统。
- 入门区分“认识概念”和“独立完成任务”；操作教程明确能完成哪一步。
- 工具演示突出具体工作任务和被省去的步骤，而不是工具名列表。
- 例：`用 React 给任务看板加上拖拽排序`；`用 ripgrep 查日志：找出失败请求的上下文`。

### Debug／踩坑

- 搜索用户优先保留症状或错误中最有辨识度的部分；错误过长时只保留能定位问题的片段。
- 多个可能原因时，“排查”通常比“彻底解决”更符合范围；仅覆盖一个原因时保留案例限定。
- 例：`Docker 容器反复重启：从日志定位一次主进程退出`。

### 性能优化

- 有结果数字时，仅核查该标题依赖的测量记录与条件：基线、指标、数据规模、硬件或并发等，不要求无关实验字段。
- 平均耗时、尾延迟、吞吐量分别表达；某次测量不能写成无条件通用收益。
- 无充分测量时突出定位方法、瓶颈或对比过程。
- 例：`SQL 查询为什么慢？用执行计划定位一次全表扫描`。

### 比较／架构取舍

- 标明影响选择的任务、规模或约束，不把场景内优势写成全面胜出。
- 架构标题突出复杂度是否值得及其成本，不默认“更复杂就是更专业”。
- 例：`小型项目要不要上微服务？从部署和排查看成本`。

### AI 编程实测

- 结论依赖时核对工具／模型版本、任务范围、人工介入和验收结果，明确实际完成了什么。
- 测试通过不自动代表需求完整满足、安全可靠或零人工；标题使用哪项承诺，就检查其依据。
- 例：`让 AI 修一个真实 Bug：测试能否通过，改动是否越界？`。

### 新闻／版本更新

- 使用材料中的实际版本、已发布功能和可靠变更记录；缺少框架名、版本或变更内容时请求补充。
- 只在年份或版本影响判断时保留，不给稳定知识随意添加“最新版”。
- 首版不主动联网研究或推测当前功能。

### 观点／面试复习／开发记录

- 观点限定适用场景，避免用全面淘汰论替代具体论证。
- 面试复习突出实际覆盖的考点或验证方式，数量与内容对应。
- 开发记录可突出真实约束、挑战规则和过程；限制条件、结果及经历均需输入支持。

## 4. 同承诺、不同表达方向

输入：复现 React 开发环境下 StrictMode 与 Effect 重复运行，解释设计意图并演示清理逻辑；不覆盖所有重复请求原因。

- **术语／搜索**：`React StrictMode 下 Effect 为什么重复运行？`
- **症状／排查**：`React 开发时请求发了两遍？检查 StrictMode 和 Effect 清理`
- **机制／兴趣**：`React 为什么要在开发环境重复运行 Effect？`

三者围绕同一内容，不宣称 StrictMode 是所有重复请求的原因，也不把关闭 StrictMode 包装成普遍正确的修复。根据受众与入口选择，不据此预测哪个标题点击率更高。
