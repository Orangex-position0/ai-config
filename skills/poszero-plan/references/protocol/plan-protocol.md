# Plan Protocol

- For `change.md` or an existing Approved Ready task, return its execution Handoff without creating `plan.md`.
- A Plan records modules, interfaces, data flow, testing seams, and implementation direction needed by Tasks; expand architecture, `DEC-*`, coverage, and migrations only when the design requires them.
- Use four discussion stages in order. At each stage start, name the stage, its decision goal, its boundary, and its exit condition. Before moving on, summarize settled decisions, unresolved questions, and deferred topics; state whether the stage is ready to close, then wait for the user's explicit confirmation to end it. A summary or recommendation is not confirmation. Reopen an earlier stage when the user requests it or a later finding changes its decisions. Confirm existing answers without re-asking.
  1. Current system and change boundary: for an existing system, inspect relevant code and explain the current path, module locations, and affected boundaries with code evidence; for a new system, explain the system boundary, external actors, and inherited constraints without inventing existing code. Defer new architecture and task breakdown. Close when the user understands where the change belongs or what the new system must own; return Spec conflicts upstream.
  2. Module boundaries and responsibilities: assign major behaviors to existing or necessary new modules, explain dependency direction, and discuss consequential alternatives. Defer function signatures and task lists. Close when each major behavior has an owner and the user understands the rationale.
  3. Key data and interactions: trace the main path and a consequential failure path through the modules; identify necessary value sources, state and resource ownership, state changes, collaboration-critical inputs, outputs, signatures, and calls. For relevant high-impact mechanisms, identify the invariant, commit point, partial-failure result, and recovery owner. Address affected error handling and migrations. Skip ordinary helper functions. Close when necessary values have sources and key handoffs are clear to the user.
  4. Technical decisions, verification, and review: resolve consequential remaining choices and high-impact risks, cover each active requirement with implementation and verification direction, and complete Developer Orientation using actual code locations when code exists. Verify feasibility of design-critical technical assumptions or make the experiment the first task before committing to a dependent design. Present the Plan revision, gaps, and readiness recommendation. Close the discussion only on the user's explicit confirmation, then separately request direct approval of the specific Plan revision; stage closure is not document approval.
- Reference approved public API contracts from Spec; Plan assigns implementation ownership and internal interactions without redefining caller-visible semantics. Write a Plan Handoff for Tasks. Do not repeat the full Spec.
