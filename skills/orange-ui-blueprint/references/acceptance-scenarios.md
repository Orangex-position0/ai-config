# 验收场景

修改或验收 skill 时使用。阅读指令只能算静态走查，不能据此宣称模型行为或 设计工具集成通过。

## 执行协议

按实际执行深度分别记录以下层级，不用低层级结果替代高层级：

1. **结构检查**：Frontmatter、内部链接、模板占位符和注释结构。
2. **静态流程走查**：逐项对照受影响的分支检查，定位对应指令和失败防线。
3. **实际模型执行**：在新会话输入固定测试请求，观察模型实际调用、关卡停留和产物；模型复述规则不算通过。
4. **真实设计工具或 HTML 原型试用**：在用户授权环境中验证当前交付模式的实际读写、回读、视觉证据和恢复。

每次验收按执行顺序分配不复用的 `test-NNN` Run ID，并使用统一记录：

| Run ID | 场景 | 执行层级 | 输入与环境 | 实际结果 | 证据 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |

结论只使用“通过 / 失败 / 阻塞 / 未执行”。阻塞和未执行均不计为通过。每次修改至少执行结构检查，并静态走查所有受影响场景；修改 description 时还要执行全部调用判别；修改设计工具写入、证据或恢复行为时，完整验收必须包含基准案例的实际模型执行和当前选定设计工具的真实试用；修改 HTML 原型分支时，必须包含 HTML 原型试用。任一受影响场景失败，则对应行为尚未通过验收。

## 调用判别

| 固定测试请求 | 预期 |
| --- | --- |
| “从这份 PRD 开始，逐阶段生成并确认 Web UI。” | 调用本 skill，默认 `hybrid-html-first`，先执行项目预检，不连接设计工具 |
| “从这份 PRD 开始，逐阶段生成并确认可编辑 Figma Web UI。” | 调用本 skill，选择 `editable-design-tool` 和 Figma；项目预检、PRD 确认后再执行工具预检 |
| “从这份 PRD 开始，逐阶段生成并确认可编辑 Penpot Web UI。” | 调用本 skill，选择 `editable-design-tool` 和 Penpot；项目预检、PRD 确认后再执行工具预检 |
| “恢复 `docs/ui/task-app/progress.md` 中的 orange-ui-blueprint 进度。” | 调用本 skill，按已记录交付模式和当前视觉载体恢复 |
| “帮我设计一个更好看的任务管理页面。” | 不调用本 skill，交给通用 UI 设计流程 |
| “把这个 Figma 页面实现成 React。” | 不调用本 skill，交给前端实现流程 |

实际模型执行以是否进入本 skill 的关卡和状态流程为判定依据，不以模型声称调用了某 skill 为证据。

## 基准案例

个人任务管理 Web 应用，首条 User Flow 为“创建任务 → 查看列表 → 标记完成”。默认模式固定测试请求为：“为个人任务管理 Web 应用逐阶段生成 Web UI，首批设计‘创建任务 → 查看列表 → 标记完成’，每个关卡等待我确认。”先完成 HTML 原型并 Review，再分别试用“不晋升”和“批准晋升到 Penpot”分支。该案例仅用于试用，不作为用户项目的默认模板。设备、主题、品牌与 Prototype 要求仍需用户确认。

## 分支检查

| 场景 | 预期行为 | 失败信号 |
| --- | --- | --- |
| 默认 HTML-first 且尚未批准晋升 | 完成项目、PRD、品牌、视觉和 HTML 工作，不连接或预检设计工具 | 因默认 Penpot 不可用而阻塞前期流程 |
| 批准晋升后设计工具不可用 | 晋升预检阻塞，说明原因并让用户保留 HTML、选择其他工具或补齐能力 | 自动切换工具或静默取消晋升 |
| 设计工具仅有读取权限 | 晋升预检阻塞，说明无法创建可编辑设计 | 把读取成功当作写入成功 |
| 工具说明声称支持写入，但未取得实际写入及回读证据 | 晋升预检保持阻塞，记录未验证能力 | 把工具说明当作实际能力证据 |
| 能创建图层但无法进行视觉检查 | 晋升预检保持阻塞，说明缺少的验收能力 | 仅凭结构写入通过预检 |
| 当前工作目录不是承载设计文档的用户项目 | 项目预检确认实际项目根目录和可写文档落点后再建档 | 默认写入当前目录 |
| `docs/ui/` 下已有同名项目 | 确认恢复现有项目或改用其他 slug | 覆盖现有文件或自行追加后缀 |
| 文档目录不可写 | 项目预检保持阻塞并报告实际错误 | 连接设计工具或进入 PRD |
| 晋升清单要求 Prototype，但工具能力不可用 | 晋升预检阻塞，说明受影响范围并等待用户调整范围、补齐能力或保留 HTML | 把基础写入能力当作 Prototype 能力通过 |
| 晋升范围不要求 Prototype 或多主题 | 对对应能力记录不适用，不为未进入范围的能力阻塞 | 强制要求所有可选能力均可用 |
| 范围变化引入新的设计工具能力 | 执行受影响操作前增量复检，只检查新增或受影响能力 | 沿用旧预检结论或重检全部无关能力 |
| 写入中途失败 | 保存成功节点、失败操作与恢复位置，停止 | 标记完成或自动重试 |
| 写入超时但实际上已创建 | 标记结果未知；用户回应且预检恢复后先回读核实，再决定继续或重试 | 把超时当作未创建并重复写入 |
| 未知写入结果无法核实 | 请求用户确认并保持阻塞 | 猜测操作成功或失败 |
| 只有一句产品想法 | 项目预检通过后列出 PRD 缺项，询问是否继续讨论 | 自行补造需求并进入品牌阶段 |
| PRD 存在选择型缺项 | 每次提供至少 2 个有实质差异的选项及取舍，保持中立并等待用户决定 | 只给一个方案、伪造近义选项或预先标记推荐项 |
| PRD 存在事实型缺项 | 直接询问事实并记录答案 | 为未知事实编造候选答案 |
| 用户明确要求推荐 PRD 选项 | 先复述目标与取舍，再给出有依据的建议并等待确认 | 用未经确认的偏好直接替用户决定 |
| PRD 未说明无障碍目标或内容本地化约束 | 列出缺项及设计影响，等待用户决定目标或明确不适用 | 默认宣称 WCAG 合规，或静默忽略文本扩展和 RTL |
| 用户拒绝补齐 PRD | 保持当前阶段，等待用户决定 | 当作默认接受建议 |
| 已有完整 PRD | 引用原文件，核验内容后请求确认 | 重写出第二份需求来源 |
| 用户要求修改品牌 | 留在品牌阶段并重新请求确认 | 同时推进视觉方向 |
| 无 Logo、Slogan | 请求明确处理决定，记录文字标识或不需要 | 静默省略或宣称正式 Logo 已完成 |
| 尚未选择视觉方向 | 展示 2～3 个参考驱动候选，等待确认 | 先生成 Design System |
| Design System 尚未确认 | 停在规范关卡 | 提前绘制业务页面 |
| 本批状态范围未确认 | 展示页面和状态清单并等待 | 一次生成整个产品 |
| HTML 页面已创建，但清单中存在未映射或未检查的适用状态 | 记录缺口并保持逐功能设计进行中或阻塞 | 提前进入人工 Review |
| HTML Review 通过但用户未决定是否晋升 | 展示晋升价值、范围和默认预算，等待决定 | 自动连接 Penpot 或开始写入 |
| 用户拒绝晋升 | 冻结 HTML 版本和批准截图，记录“不晋升”并交接 | 继续预检或写入设计工具 |
| 用户批准晋升 | 先确认关键资产清单和预算，再执行工具预检 | 完整复制所有 HTML 页面和状态 |
| 晋升范围超过 1 Flow、5 页面或 1 主尺寸 | 报告新增价值和预计操作量，等待扩展预算批准 | 静默超预算或以多轮小调用规避预算 |
| 晋升批次写入完成 | 合并执行一次结构回读和一次视觉检查 | 为每个节点单独回读和留证 |
| Review 检查项缺少结论或证据 | 补齐检查结果并保持进行中 | 仅凭整体观感请求最终确认 |
| 已确认 WCAG 目标，但只完成静态设计工具或 HTML 检查 | 记录已检查的设计项及运行时交接要求 | 宣称运行时无障碍合规已通过 |
| 本轮要求长文本或 RTL，但相关布局未设计和检查 | 记录缺口并保持进行中 | 仅以默认语言页面通过 Review |
| Review 问题未解决且用户未明确接受 | 保持待确认或进行中 | 开始下一批或标记验收通过 |
| 修改已确认 PRD | 比较证据，标记受影响部分并请求修改范围确认 | 沿用旧确认或全部无差别重做 |
| 文档和选定设计工具或 HTML 原型冲突 | 记录差异，暂停相关工作，请用户决定 | 静默选一边覆盖另一边 |
| 新会话恢复 | 只读进度定位目标，再预检、比较版本和恢复 | 预检前推进阶段，或仅凭已完成标记跳阶段 |
| Git 工作区有未提交设计文档 | 保存待确认内容快照 | 用不匹配的 HEAD 代表当前内容，或自动提交 |
| 无 Git 的项目 | 保存完整文档快照并记录确认章节 | 仅递增版本号却无法取回旧内容 |
| 恢复时已有关闭记录或 ID 序号存在间隔 | 从现存最大序号继续分配，不复用历史 ID | 从记录数量推算或填补旧编号 |
| 待确认版本修订后重新展示 | 分配新的 review-NNN，并保留旧 evidence | 覆盖旧快照或沿用旧 Review ID |
| 一个晋升 Review 包含多个关键页面 | manifest 记录关键页面定位，共享一次批次结构证据并分别映射视觉证据 | 为每个节点重复保存完整结构，或只保存文件级链接 |
| 必要证据无法持久化 | 保持待确认并报告缺口 | 创建空文件、占位内容或仅用时间戳代替 |
| 文档仅有格式变化 | 对比基线并记录无设计影响 | 重跑设计流程 |
| 待确认内容在用户回复前变化 | 展示新版本并重新请求确认 | 把回复绑定到用户未看过的内容 |
| 后续章节新增内容 | 只比较原确认章节的内容 | 因完整文件变化使所有阶段失效 |
| 已保存的设计工具版本无法回读 | 使用已保存的结构及视觉快照；无基线则待重新审核 | 用节点链接或时间戳冒充历史内容 |
| 用户只修改文档未批准 | 识别差异并请求明确确认 | 把文件保存当作审批 |
| HTML 原型只有整页图片 | 判为未满足原型交付条件，除非用户明确选择视觉参考模式 | 宣称 HTML 原型完成 |
| 设计工具晋升交付只有整页图片 | 判为未满足可编辑交付条件 | 宣称可编辑设计稿完成 |
| 已有批准 Penpot 基线后的普通文案、间距或 Bug 修复 | 默认以代码为准，不要求回写 Penpot | 每次前端变化都强制同步设计工具 |
| Tokens、品牌、公共组件结构、核心 Flow、信息架构或主要布局变化 | 标记相关设计基线待更新，在里程碑同步 | 只改代码且不记录基线漂移 |
| 用户未要求 Prototype | 不默认制作工具 Prototype 连线；HTML 只实现本批已确认演示交互 | 自行扩展交付范围 |

## 真实设计工具或 HTML 原型试用

在用户授权的试用环境中执行基准流程，逐关卡取得实际确认。按当前交付模式检查：

- 项目预检只验证文档落点和执行定位；默认 HTML-first 在晋升决定前不连接设计工具。
- PRD、品牌、视觉方向、Design System、HTML Flow Review 顺序可追踪，每次确认绑定实际版本。
- HTML/CSS 原型：源码可读取、入口可运行、页面结构、演示交互和代表性状态符合已确认范围，且保存批准截图。
- 不晋升分支冻结 HTML 后可以直接交接，不因设计工具状态阻塞。
- 晋升分支先确认关键资产清单和预算，再验证工具写入、回读、视觉检查及实际范围能力。
- 可编辑设计工具中的文本及布局可编辑，公共 UI 引用组件；必要 Variants、Auto Layout 和 Prototype 符合晋升清单。
- 每个晋升批次只保存一次合并结构回读和关键页面视觉证据，不逐节点重复取证。
- 更改一项上游决策后，仅受影响的产物进入重新审核。
- 恢复会话可以定位当前视觉载体和阶段，未重新执行已成功的创建操作。
- 交付只声明设计结果；前端实现和 Browser Screenshot 对批准截图属于后续流程。

使用执行协议中的统一记录分别报告四个层级；没有执行的层级标记“未执行”，不补写模拟通过记录。完整通过要求基准案例在四个层级均为“通过”，且本次修改影响的分支检查没有失败或阻塞。
