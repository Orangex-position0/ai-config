# Orange UI Blueprint

把需求逐步收敛成可运行、可审核、可交接的 HTML 原型，再按实际交付价值选择性晋升为可编辑设计稿。默认以 HTML 快速完成设计探索和完整流程；Penpot 是默认晋升工具，也可配置 Figma 或其他经验证的工具。

## 输入、产物与边界

先确定项目级字段并写入 `progress.md`：

- `delivery-mode`：默认 `hybrid-html-first`；用户明确只需原型时可选 `html-prototype`，明确要求直接使用设计工具时可选 `editable-design-tool`，只需图片参考时可选 `visual-reference`。
- `design-tool`：默认晋升目标为 `penpot`，也可选择 `figma` 或其他工具；它不表示流程开始时连接该工具。
- `active-visual-carrier`：记录当前视觉工作稿位于 HTML、设计工具或视觉参考。

`hybrid-html-first` 先交付独立可运行的 HTML/CSS 原型。原型可包含少量演示交互，但不接真实 API、认证或生产状态，不进入生产源码目录，也不冒充生产实现。可编辑设计工具只承载核心 Tokens、公共组件、关键页面和代表性状态，不镜像完整 HTML。

- 接收产品想法或已有 PRD；品牌资产、参考图、技术与业务约束可选。
- 首版面向 Web UI；交付范围仅包含 PRD 明确确认的尺寸、响应式范围、主题、无障碍目标、内容与本地化约束及 Prototype。
- HTML 原型覆盖本批完整 User Flow、适用状态和已确认尺寸；设计工具晋升只覆盖获批的关键资产。
- 前端实现与运行时 UI 验证属于后续流程；本 skill 不编写生产代码。

## 0. 项目预检

开始或恢复时，先只读已有 `progress.md` 以定位项目和执行位置。无记录时确认目标、交付模式、默认晋升工具、本地项目根目录和 lowercase-hyphens 项目 slug。确认 `docs/ui/` 可写；发现同名目录时按文档契约确认恢复还是使用其他 slug，不擅自覆盖。

默认流程此时不连接或预检 Penpot、Figma 等设计工具。只有以下分支需要设计工具预检：

- 用户明确选择 `editable-design-tool`；在 PRD 确认、工具范围已知后预检。
- HTML 原型通过 Review，用户批准晋升；在任何设计工具写入前预检。

完成条件：交付模式、默认晋升工具、本地项目根目录、文档目录及项目 slug 均已明确；文档落点可写；同名目录处理已确定。PRD 仅在这些条件满足后开始。

执行中出现阻塞性故障时，仅保存已有进度、成功节点、失败操作及其目标，使用以下格式报告并停止：

```text
阻塞位置：阶段 / 操作
失败证据：实际错误或未能核实的能力
已保留进度：文档 / 节点 / 结果未知的操作
需要用户处理或决定：解除阻塞所需动作
```

写入超时或返回不明确时，进入独立的“结果未知”状态。用户回应且预检通过后，先回读目标区域，再依据实际结果继续或重试；回读仍无法判定时请求用户确认。用户若明确改做文档任务，说明已离开本 skill 的完整交付流程。

## 持久化与状态

项目预检通过后，读取 [文档契约](references/document-contracts.md)，在用户项目的 `docs/ui/<project>/` 保存：

- `design-spec.md`：PRD、品牌、视觉方向、Design System 四个独立章节。
- `progress.md`：阶段状态、确认版本、设计工具定位、批次、阻塞项和下一步。
- `flows/<flow>.md`：各流程页面、交互状态、设计节点及 Review 记录。

阶段独立不等于文件独立。逐阶段填写，不预先编造未来阶段内容；文档过长才按用户同意拆分。已有 PRD 引用原文件，不另建相互竞争的副本。

采用以下轻量状态表记录流程：

| 状态 | 转换条件 |
| --- | --- |
| 未开始 → 进行中 | PRD 阶段要求项目预检通过；后续阶段要求前置阶段已确认，涉及设计工具写入时还要求对应工具预检通过 |
| 进行中 → 待确认 | 阶段产物持久化，自检完成，向用户展示具体版本 |
| 待确认 → 已确认 | 用户明确批准该版本；记录原意、时间和版本证据 |
| 待确认 → 进行中 | 用户要求修改；更新后重新请求确认 |
| 已确认 → 待重新审核 | 本阶段或上游变化影响原确认 |
| 待重新审核 → 进行中 | 用户确认影响范围及修改计划 |

阻塞是叠加状态：记录阻塞前的阶段和状态，解除后回到原位置，不自动通过关卡。

每个阶段及流程范围确认都是独立关卡。先按文档契约固定待确认版本，再使用以下格式等待用户回应：

```text
当前关卡：阶段 / 流程范围 / 流程验收
待确认产物：文档路径 / 设计工具链接或定位信息（适用时）/ 版本证据
已完成：自检结论及已知限制
需要你决定：未决项；是否确认该版本
确认后进入：下一阶段或操作
```

单次确认仅针对已展示且此后未变化的产物版本；拒绝、沉默、修改文件或笼统的后续授权均不代替各关卡验收。

## 1. PRD

按文档契约链接的 design-spec 模板中 PRD 字段检查输入，将本轮范围和设计批次收敛到可验收的用户目标。

发现缺项时，列出缺项及其设计影响，显式询问：“PRD 尚不完整，是否继续讨论并补齐这些内容？”等待同意后，按设计影响从高到低逐项讨论：

- 事实型缺项直接询问事实，例如已有用户、业务规则或技术限制。
- 选择型决策每次提供至少 2 个有实质差异的可行选项，分别说明对用户目标、设计范围和后续成本的影响，并允许用户提出自定义方案。
- 用户说明偏好或明确要求建议前，各选项保持中立排序，不标记默认项或推荐项。
- 用户要求建议时，先复述用于判断的目标与取舍，再给出有依据的建议；该建议仍需用户明确确认。

用户不继续时保持当前阶段，答案仅来自用户后续输入。已有 PRD 只检查和补齐缺项。

完成条件：事实型缺项已有明确答案；每个选择型决策都经过选项比较并记录用户决定；上述信息足以确定本轮设计范围、非目标及流程设计批次，且用户确认 PRD。

### 交付范围复核

PRD 确认后记录 HTML 原型需要覆盖的流程、状态、尺寸、主题和交互。默认分支只核实本地原型的运行、结构读取和截图能力，不为尚未批准的 Penpot / Figma 晋升付出连接成本。

用户明确选择 `editable-design-tool` 时，才从已确认范围推导所需工具能力并执行下文“设计工具晋升”中的预检。缺少必要能力时保持阻塞，让用户调整范围、补齐能力或明确切换为 HTML-first；不静默切换交付模式。

## 2. 品牌信息

按 design-spec 模板单独补齐品牌信息及资产来源。

- 确认 Product Name 和 Brand Keywords 后才能进入视觉方向。
- Logo 使用已有资产；缺失时提出方向，由用户提供、交给专门工具，或明确批准本轮使用文字标识。本 skill 不承担正式 Logo 制作。
- 可协助拟定 Slogan；Logo、Slogan 每项都记录用户选择的资产、文字方案或“不适用”决定。

完成条件：四项均有明确决策，资产链接或不制作决定已记录，用户确认品牌信息。

## 3. 视觉方向

依据已确认 PRD 和品牌，提供 2～3 个有实质区别的候选方向。使用用户提供或搜集的 Reference；可参考 Dribbble、Behance、Mobbin、Pinterest、设计工具社区、同类产品。

按 design-spec 模板记录各方向，用可查看的视觉证据比较产品适配性。引用参考与复用素材分开处理，参考不等于资产授权。来源无法查看时标记为未验证，视觉描述仅依据实际观察证据。

完成条件：用户选定或修订一个方向并确认；其他候选标记未采用，后续设计仅使用最终方向。

## 4. Design System

独立执行，先建立规范再画业务页面：

**Design Tokens → Basic Components → Composite Components → Page Layout**

以 MVP 实际需要为范围落地 Tokens、可复用展示组件和布局规则。`hybrid-html-first` 与 `html-prototype` 先在 HTML 中实现；`editable-design-tool` 在工具预检通过后直接在工具中实现。覆盖适用状态及已确认主题；HTML 分支不为展示原型引入生产级状态架构。

文档记录关键 Tokens、组件约定和当前载体定位。检查结构和视觉结果，并按已确认无障碍目标检查一致性、文字可读性、对比度、Focus 表达、目标尺寸及非颜色提示；运行时语义和辅助技术行为进入开发交接，当前结论限定为静态设计检查。

`hybrid-html-first` 获批晋升后，再把核心 Tokens、公共组件及必要 Variants 选择性重建到工具中；完整 HTML 不做双向同步。

完成条件：本轮所需规范、组件、状态及布局规则在当前视觉载体中可编辑且可定位；文档同步，用户确认。后续发现缺少组件时，先补充并确认受影响的 Design System，再用于页面。

## 5. 逐功能 UI 设计

以可完成用户目标的一条 User Flow 为设计批次，不一次生成整个产品。每批开始前读取已确认 PRD、品牌、视觉方向和 Design System：

1. 列出本批入口、操作路径、结果、页面和状态清单，持久化并请求用户确认。
2. 默认在 HTML 原型中使用已确认组件与 Tokens 生成完整流程；`editable-design-tool` 则在已预检工具中生成已确认范围。只补齐实际适用的状态，并记录需要解释的排除项。
3. 检查当前载体的结构、组件复用和目标尺寸下的视觉结果；HTML 记录运行入口、关键源码定位和批次截图，设计工具记录稳定定位和批次证据。
4. 进入本批人工 Review；HTML-first 确认后决定是否晋升设计工具，再开始下一批。

完成条件：范围确认记录仍有效；清单中的每个适用“页面 × 状态”均有当前载体定位；需求、组件与 Tokens、目标尺寸及主题、结构检查和视觉证据可追踪。人工 Review 仅在全部适用项完成验证后开始。

## 6. Review、修改与确认

逐项核对：

- PRD 需求与验收标准是否覆盖，是否出现越界功能。
- 页面层级、内容组织和用户操作路径是否清晰、完整。
- 是否遵循 Design System，重复组件是否复用。
- Hover、Focus、Loading、Empty、Error、Disabled 等适用状态是否完整。
- 已约定的尺寸、响应式、主题与 Prototype 是否覆盖。
- 已确认的无障碍目标是否落实到适用的对比度、Focus、目标尺寸、非颜色提示及交接要求。
- 主要语言、文本扩展、日期与数字格式、RTL 等适用的内容和本地化约束是否覆盖。
- HTML 页面是否由可读取源码组成；设计工具页面是否由可编辑文本和图层组成，并在适用时使用 Auto Layout；两者均不得用整页截图冒充。
- 文档、当前视觉载体与实际结构和视觉证据是否一致。

把问题、严重程度、修改意见及验证结果写入当前流程文档。展示设计供用户 Review，修改后重新检查并请求确认。

完成条件：清单中的每个检查项都有“通过 / 有问题 / 不适用”结论及证据或原因；每个问题均已复核解决，或由用户明确接受该具体遗留项及后续处理；需求 ID → 页面 / 状态 → 当前视觉载体定位 → Review 结果完整可追踪；用户确认绑定未变化的验收基线，`progress.md` 已记录有效确认。缺项保持待确认或进行中。

## 7. 设计工具晋升

`hybrid-html-first` 的 HTML 原型通过 Review 后，明确询问是否需要可编辑设计工具交付。用户拒绝时冻结本次 HTML 版本和截图，记录“不晋升”，继续交接；不把 Penpot 当作默认必做步骤。

用户批准晋升时执行以下完整流程。`editable-design-tool` 在 PRD 确认后先执行第 1～3 步，再以该工具完成 Design System、逐功能设计与 Review，并按第 5～6 步取证确认。

1. 确认工具、目标文件、授权范围和本批晋升清单。清单默认只含核心 Tokens、公共组件、每条核心 Flow 的 3～5 个关键页面及每类代表性状态。
2. 发现可用集成并读取实际工具说明。核实定位或创建文件、编辑文本/图层/布局、结构回读、视觉检查、证据保存和稳定定位能力；写入探测须经用户同意并放在隔离区域。
3. 按 PRD 仅复检实际需要的 Variables / Modes、Variants、Prototype、Styles、导出等范围能力。缺能力时保持阻塞，让用户缩小范围、补齐能力或保留 HTML 交付。
4. 依据已批准 HTML、Tokens 和组件规则选择性重建，不做整站转换，不逐页复制可由规则推导的重复状态。
5. 每批合并写入；完成后执行一次批次结构回读和一次视觉检查。超时或返回不明时标记“结果未知”，恢复后先回读再决定是否重试。
6. 保存关键页面定位、合并结构证据和批准截图，请求用户确认设计工具基线。确认后冻结对应 HTML 工作稿，不维持双向同步。

### 默认预算

除非用户批准扩展，每个设计工具批次限制为：

- 1 条核心 User Flow、最多 5 个关键页面、1 个主要目标尺寸。
- 核心 Tokens、公共组件和代表性状态；重复页面与状态通过规则交接。
- 1 次合并结构回读、1 次视觉检查；单项失败最多重试 1 次。
- 超预算前报告新增范围、价值和预计操作量，等待批准。

完成条件：晋升清单、工具能力和预算均已确认；清单内资产可编辑且可定位；批次级结构与视觉证据可取回；用户确认未变化的设计工具基线。

## 恢复、变更与冲突

恢复顺序：只读 `progress.md` 定位项目、交付模式、当前视觉载体和阶段 → 项目预检 → 读取相关文档与确认版本 → 恢复 HTML 原型；仅在已有设计工具晋升或直接工具模式下复检工具能力。版本保存与比较方式遵循文档契约；无法核实旧版本时标记待重新审核。

上游变更时保留现有产物，列出受影响的决策、组件和页面，将相关确认标记待重新审核，回到最早受影响阶段。用户确认修改范围后，只重做受影响产物。

使用以下权威层级处理冲突：PRD 负责业务规则与验收条件；HTML 是探索阶段视觉工作稿；已批准的设计工具关键页面是视觉基线；前端代码上线后是运行时事实。发现不一致时记录差异并暂停受影响工作，由用户判断实现错误、合理演进或需要更新设计基线，不静默同步覆盖。

## 交付与后续流程

所有本轮流程通过 Review 后，核对文档、冻结的 HTML 原型和已晋升的设计工具关键资产。在现有文档中整理运行入口、批准截图、设计节点、Tokens、组件定义、状态与响应式约定、需求映射和用户已接受的遗留项，并输出路径与链接。

前端交接包含 PRD、Tokens、组件约定、关键页面、交互说明和批准截图。原型源码仅供参考，不默认复制到生产项目。后续流程为：

1. 前端实现：结合技术栈与项目规范重新实现状态架构、语义、性能和测试。
2. UI 验证：以 Browser Screenshot 对比批准截图；AI 可辅助分析差异，人工裁决实现错误、合理演进或设计基线更新。
3. 设计工具维护：仅在 Tokens / 品牌、公共组件结构、核心 Flow、信息架构、主要布局、正式关键页面或版本里程碑变化时更新。文案、间距微调、Bug 修复和响应式细节默认以代码为准。

这些步骤属于后续流程；本 skill 的完成状态仅覆盖设计交付。

修改或验收本 skill 时，使用 [验收场景](references/acceptance-scenarios.md)，分别报告结构检查、静态流程走查、实际模型执行和真实设计工具或 HTML 原型试用的验证范围。
